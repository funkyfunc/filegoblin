# Releasing filegoblin

A release is one tag push. `.github/workflows/release.yml` (generated by
[dist](https://opensource.axo.dev/cargo-dist/); regenerate it with
`dist generate --mode ci` after changing `dist-workspace.toml`, never by hand)
does the rest.

```bash
# bump the version in crates/cli/Cargo.toml and crates/core/Cargo.toml, then
git commit -am "release: v1.15.0"
git tag v1.15.0
git push origin main v1.15.0
```

## What a release produces

| Job | Output |
|---|---|
| `build-local-artifacts` (dist) | `filegoblin-<target>.tar.xz` / `.zip`: the **lite** build for 5 targets |
| `custom-vision-models` → `build` | `filegoblin-vision-models.tar.gz` (+ `.sha256`): the models alone. `filegoblin --install-models` downloads this file |
| `custom-vision-models` → `full` | `filegoblin-full-<target>.tar.xz` / `.zip`: one binary with the models compiled in (`bundled-models`) |
| `custom-vision-models` → `registry-packages` | PyPI wheels and npm packages, built and smoke-tested (not attached to the release) |
| `host` (dist) | the GitHub release, with everything above except the registry packages |
| `custom-publish-packages` | uploads to PyPI and npm |

**Package names:**
- **PyPI:**
  - `filegoblin`: one wheel per platform.
  - `filegoblin-models` and `filegoblin-models-part1…N`: the weights, installed by `filegoblin[models]`.
- **npm:**
  - `filegoblin`: the launcher, from `npm/`.
  - `filegoblin-<os>-<cpu>`: one package per platform with the binary.
  - `filegoblin-models` and `filegoblin-models-part1…N`: the weights.
- **Building locally:** `scripts/package_registries.py` builds all of these from dist's archives and the model archive.

The weights are split into pieces under 90 MiB, named `<model>.part<i>of<n>`. This keeps them under PyPI's 100 MB per-file limit, and under the size limits of company package mirrors. filegoblin joins the pieces when it loads a model.

## One-time registry setup

Until a registry is set up, its publish job is skipped with a warning; the GitHub release goes out regardless.

**PyPI.** Choose one of these:
- **A token:** create an API token on pypi.org and add it as the repository secret `PYPI_API_TOKEN`. The first upload creates the projects, so the token must be account-wide at first. Once the projects exist, replace it with a token scoped to them.
- **Trusted publishing:** on pypi.org, add a pending publisher for each project name: `filegoblin`, `filegoblin-models` and `filegoblin-models-part1` through `part6`. Use repository `funkyfunc/filegoblin`, workflow `release.yml`, and no environment. Then set the repository variable `PYPI_TRUSTED_PUBLISHING` to `true`.

Each release adds about 510 MB across the model projects. PyPI allows 10 GB per project; when a model project gets close, delete old releases of it.

**npm.** Create an automation token on npmjs.com for the account that owns `filegoblin`, and add it as the repository secret `NPM_TOKEN`. The platform and model packages are unscoped (`filegoblin-linux-x64`, `filegoblin-models-part1`, …), so no npm organisation is needed.

Re-running a publish job is safe: versions that are already on a registry are skipped.
