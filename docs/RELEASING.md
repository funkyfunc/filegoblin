# Releasing filegoblin

A release is one tag push. `.github/workflows/release.yml` (generated by
[dist](https://opensource.axo.dev/cargo-dist/); regenerate it with
`dist generate --mode ci` after changing `dist-workspace.toml`, never by hand)
does the rest. Agents: release only when asked; registry versions are
permanent.

## At a glance

| Where | What | Published by |
|---|---|---|
| [GitHub release](https://github.com/funkyfunc/filegoblin/releases) | `filegoblin-<target>` (lite), `filegoblin-full-<target>` (models compiled in), `filegoblin-vision-models.tar.gz` | `release.yml` (dist) |
| [PyPI](https://pypi.org/project/filegoblin/) | `filegoblin`, one wheel per platform. The nine model projects aren't on PyPI yet ([Model packages on PyPI](#model-packages-on-pypi)) | `publish.yml`, environment `pypi` |
| [npm](https://www.npmjs.com/package/filegoblin) | `filegoblin` (launcher), five `@filegoblin/<os>-<cpu>`, `@filegoblin/models` and eight `@filegoblin/model-*` | `publish.yml`, environment `npm` |

State as of v1.15.0 (2026-10-17): every npm name exists and trusts `publish.yml`; PyPI has `filegoblin` only.

**Files that pin the version** (all must equal the tag):
- `crates/core/Cargo.toml`: `version`
- `crates/cli/Cargo.toml`: `version`, and `version` on the `filegoblin-core` path dependency
- `Cargo.lock`: the `filegoblin` and `filegoblin-core` entries (`cargo check` updates them)
- `npm/package.json`: `version` and the five `@filegoblin/*` optionalDependencies (the build overwrites these, but keep them in sync)

```bash
# after bumping every file above
dist plan --tag=vX.Y.Z        # cargo-dist 0.31.0; fails if the tag and versions disagree
git commit -m "release: vX.Y.Z" crates/cli/Cargo.toml crates/core/Cargo.toml Cargo.lock npm/package.json
git push origin main
git tag vX.Y.Z && git push origin vX.Y.Z
```

Release takes about 80 minutes; Publish starts when it succeeds.

The tag must match the Cargo version: if it doesn't, Release fails at `plan`
and nothing is built. Delete the tag (`git push origin :refs/tags/vX.Y.Z`),
fix the version, and tag again.

## What a release produces

| Job | Output |
|---|---|
| `build-local-artifacts` (dist) | `filegoblin-<target>.tar.xz` / `.zip`: the **lite** build for 5 targets |
| `custom-vision-models` → `build` | `filegoblin-vision-models.tar.gz` (+ `.sha256`): the models alone. `filegoblin --install-models` downloads this file |
| `custom-vision-models` → `full` | `filegoblin-full-<target>.tar.xz` / `.zip`: one binary with the models compiled in (`bundled-models`) |
| `custom-vision-models` → `registry-packages` | PyPI wheels and npm packages, built and smoke-tested (not attached to the release) |
| `host` (dist) | the GitHub release, with everything above except the registry packages |
| `publish.yml` (its own workflow, started when Release finishes) | uploads the registry packages to PyPI and npm |

**Package names:**
- **PyPI:**
  - `filegoblin`: one wheel per platform.
  - `filegoblin-models` and one `filegoblin-model-<name>` per model: the weights, installed by `filegoblin[models]`.
- **npm:**
  - `filegoblin`: the launcher, from `npm/`.
  - `@filegoblin/<os>-<cpu>`: one package per platform with the binary.
  - `@filegoblin/models` and one `@filegoblin/model-<name>` per model: the weights.
  - Everything except the launcher is in the `@filegoblin` scope, so only members of the npm organisation `filegoblin` can publish the binaries the launcher runs.
- **Building locally:** `scripts/package_registries.py` builds all of these from dist's archives and the model archive. `scripts/package_registries.py names pypi` (or `npm`) lists every name.

The model packages are one per model, named for what it does:

| Package (`filegoblin-model-…` on PyPI, `@filegoblin/model-…` on npm) | Contents |
|---|---|
| `layout-1`, `layout-2` | page layout and reading order (PP-DocLayoutV3, 134 MB, in halves) |
| `formula-encoder`, `formula-decoder` | formulas to LaTeX (pix2text MFR 1.5) |
| `tables-1`, `tables-2` | table structure (Table Transformer v1.1, 118 MB, in halves) |
| `ocr-detector`, `ocr-recognizer` | OCR for scanned pages (PP-OCRv6 medium) |

The two models over PyPI's 100 MB per-file limit come in halves; company package mirrors often have the same limit. filegoblin joins the halves when it loads the model. The splits are fixed in `MODEL_PACKAGES` in `scripts/package_registries.py`, so the names never change, and the build fails if a model outgrows its split.

## One-time registry setup

Both registries use **trusted publishing**: no tokens are stored in the repository. Each registry trusts one workflow file plus one GitHub environment, and pushing the tag is the approval. Neither environment has protection rules; GitHub creates them on first use.

| Registry | Workflow | Environment |
|---|---|---|
| PyPI | `publish.yml` | `pypi` |
| npm | `publish.yml` | `npm` |

The publishing lives in `publish.yml`, not in the dist-generated `release.yml`, because PyPI's trusted publishing does not work from reusable workflows ([pypa/gh-action-pypi-publish#166](https://github.com/pypa/gh-action-pypi-publish/issues/166)), and dist's publish jobs are reusable workflows. `publish.yml` starts when a tag run of Release succeeds, and downloads the packages that run built. You can also run it by hand (Actions → Publish → Run workflow) with the ID of a Release run. Prereleases (`v1.2.3-rc.1`) are not published automatically.

**PyPI.** There are ten projects. `scripts/package_registries.py names pypi` prints them:
- `filegoblin`
- `filegoblin-models`
- `filegoblin-model-layout-1`, `filegoblin-model-layout-2`
- `filegoblin-model-formula-encoder`, `filegoblin-model-formula-decoder`
- `filegoblin-model-tables-1`, `filegoblin-model-tables-2`
- `filegoblin-model-ocr-detector`, `filegoblin-model-ocr-recognizer`

Every trusted publisher uses owner `funkyfunc`, repository `filegoblin`, workflow `publish.yml` and environment `pypi`.

A project that doesn't exist yet needs a **pending publisher** (pypi.org → Your account → Publishing); the first upload through it creates the project. An account can hold at most three pending publishers at once, so the ten can't all start this way:
1. Add a pending publisher for `filegoblin` only, and push the release tag soon after. A pending publisher doesn't reserve the name.
2. Until the model projects exist, the "Base package only" step in `publish.yml` deletes the model wheels before the upload, so a release publishes just the `filegoblin` wheels.
3. Once `filegoblin` is live, create the nine model projects by hand, once (see [Model packages on PyPI](#model-packages-on-pypi)).

Each release adds about 510 MB across the model projects. PyPI allows 10 GB per project, so when one gets close, delete its old releases.

**npm.** npm only lets you configure a trusted publisher on a package that already exists, and trusted publishing cannot do a package's first publish. `scripts/npm-bootstrap.sh` handles both steps. Run it yourself, logged in to npm with 2FA and npm 11.15 or later:
1. It publishes a deprecated `0.0.0-bootstrap` placeholder for each `@filegoblin/…` package that does not exist yet.
2. It points every package, `filegoblin` included, at `publish.yml` with environment `npm` using `npm trust github`.

A new trusted-publisher configuration expires if nothing publishes with it within two days, so run the script shortly before pushing the release tag. The script takes its package names from `package_registries.py names npm`. If a model package is ever added, run it again (it skips what already exists). The new PyPI project needs a publisher too: a pending one, or a first upload by hand as in [Model packages on PyPI](#model-packages-on-pypi).

Re-running `publish.yml` is safe: versions that are already on a registry are skipped.

## Model packages on PyPI

`filegoblin-models` and the eight `filegoblin-model-…` projects are created once by hand, after `filegoblin` is on PyPI:

1. Create an account-scoped API token on pypi.org. A token scoped to one project can't create projects.
2. Download the packages from the Release run for the same version as the published `filegoblin`. Artifacts are kept for 30 days.
   ```bash
   gh run download <release-run-id> -R funkyfunc/filegoblin -n registry-packages
   ```
3. Upload the model wheels:
   ```bash
   TWINE_USERNAME=__token__ uvx twine upload wheels/filegoblin_model*   # paste the token when asked
   ```
4. On each of the nine new projects (Manage → Publishing), add a trusted publisher with the four values above.
5. Delete the token, and delete the "Base package only" step from `publish.yml`.

Until then, `pip install "filegoblin[models]"` doesn't resolve. `filegoblin --install-models` gets the models from the GitHub release instead.

## When something goes wrong

| Symptom | Cause and fix |
|---|---|
| Release fails at `plan` (exit 255), suggesting `--tag=v<other>` | The tag doesn't match the Cargo versions. Delete the tag (`git push origin :refs/tags/vX.Y.Z` and `git tag -d vX.Y.Z`), bump every file listed above, tag again. |
| Publish didn't start | It only runs after a successful Release for a non-prerelease tag. Start it by hand: Actions → Publish → Run workflow, or `gh workflow run publish.yml --ref main -f run-id=<release run id>`. |
| A fix to `publish.yml` doesn't apply on "Re-run jobs" | Reruns use the workflow file from the tagged commit. Use Run workflow (above), which uses `main`'s. |
| npm `E409 Cannot publish over previously staged version` | An earlier run already uploaded it and npm is still processing it. `publish.yml` treats this as done. |
| npm `TLOG_CREATE_ENTRY_ERROR` (409) | A transient Sigstore conflict before the upload. `publish.yml` retries it. |
| npm `E404` / `ENEEDAUTH` for one package | That name doesn't exist on npm or isn't linked to `publish.yml`/`npm`: run `scripts/npm-bootstrap.sh` yourself, logged in to npm (it needs your 2FA/passkey, so an agent can't). |
| A version published fine but `npm view` doesn't show it | npm takes 1–20 minutes to make a new version visible; the large model parts take longest. Wait. |
| PyPI `invalid-publisher` | No trusted or pending publisher for that project, or a mismatch in owner/repo/workflow/environment. |
| `pip install "filegoblin[models]"` fails | Expected until the model projects exist on PyPI; use `filegoblin --install-models`. |

v1.15.0 hit the `plan`, both 409 and the visibility rows, plus `npm publish` without `./` (fixed in `publish.yml`). Details: docs/ADR.md, "First registry release (v1.15.0)".
